## Aprendizajes y errores a evitar
- `verbatimModuleSyntax: true` exige `import type` para tipos.
- Node 24.21+ hace strip-types por defecto para `.ts`; no hace falta flag explícito en `node --test`.
- Tests de espera con `time.monotonic` real + `asyncio.sleep` real ⇒ loop infinito. Para ser deterministas: inyectar `clock` y `sleep`, hacer que el sleep fake avance el clock.
- En Python 3.14, `asyncio.get_event_loop().run_until_complete(...)` falla con `RuntimeError: There is no current event loop`; usar `asyncio.run(...)` o `@pytest.mark.asyncio`.
- Tareas de Docker (T4, T5, T6, T10) deben verificarse con runtime de contenedores; en este WSL2 no hay Docker/Podman instalado. No darlas por hechas solo con validación estática.
- En YAML de Compose, todos los servicios top-level deben tener la misma indentación; mezclar col-0 y col-2 hace que PyYAML los parsee como un único servicio malformado.
- Alembic offline: `command.downgrade(base, sql=True)` falla con `downgrade with --sql requires <fromrev>:<torev>`; usar `command.downgrade(cfg, "head:base", sql=True)`. Alembic escribe SQL offline a `Config.output_buffer` (no `Config.stdout`). Capturar SQL: `cfg = Config(file_=..., output_buffer=io.StringIO())`. `Config` (Alembic 1.20) NO expone `get_alembic_script()`; usar `ScriptDirectory.from_config(cfg)`.
- Importar `sqlalchemy.ext.asyncio` o `asyncpg` al top-level fuerza dependencias que rompen los tests sin greenlet/sin BD. Hacer el import dentro de la función async.
- Alembic offline: `command.upgrade(cfg, "0001:0001", sql=True)` es un no-op (fromrev == torev). Para capturar SQL de **una sola revisión intermedia**: `command.upgrade(cfg, "<revision_id>", sql=True)` (sin `:`).
- Fixture `scope="class"` definida como instance method está deprecada en pytest-asyncio (`PytestRemovedIn10Warning`); leer la fuente en module-scope y exponerla como constante.
- En archivos Python de esta sesión, `\u2019` y `\u2013` quedaron como escape literal en algunas líneas (cosmético, no afecta ejecución); el `edit` tool con JSON no los desescapa automáticamente — usar `write` o anchors únicos para no liarse.
- Alembic: `Config(str(alembic_ini))` exige que el `alembic.ini` esté dentro de la imagen. Un `Dockerfile` que sólo `COPY app`, `tests`, `pyproject.toml` produce `CommandError: No 'script_location' key found in configuration` en runtime aunque `alembic upgrade head` funcione en el host con `pip install -e .`. Hay que `COPY alembic.ini alembic/` también.
- Keycloak 24 elimina el campo `verifyEmailListedRealm` del `RealmRepresentation`. Los realm-export.json generados con Keycloak 25/26 fallan al importarse en 24 con `UnrecognizedPropertyException`. O ajustar la versión de la imagen, o regenerar el export sin ese campo. La validación estática (json parsea + nombres coherentes) no detecta esto.
- Los realm-export.json de Keycloak 24 también rechazan otros campos presentes en exports de KC ≥25 (`loginLifecycleBehavior`, `oauth2DeviceCodeLifespan`→`oAuth2DeviceCodeLifespan`, `clientType`, `authenticatorConfig`) y además KC's `CLIENT.DESCRIPTION` es `VARCHAR(255)`. Auditar contra las `*Representation.java` de release/24.0 y validar arrancando un KC 24 con `--import-realm`; las columnas limitadas a 255 chars son invisibles para el validador de esquema.
- `Path(__file__).resolve().parent.parent` desde `app/core/startup.py` da `/app/app`, no `/app`. El `alembic.ini` del proyecto está en la raíz del backend, no junto al paquete `app`. Una derivación de ruta off-by-one así pasa todos los tests si estos mockean la función que la usa; ningún test mockeado puede atrapar el path-bug. La cura: un test dedicado que cargue `Config(str(_ALEMBIC_INI))` y verifique que `script_location` se resuelve sin `No 'script_location' key found in configuration`. Aquí: 4 tests nuevos (`TestAlembicIniPath`) y la corrección a `.parent.parent.parent` en `_BACKEND_DIR`; los 3 tests reprodujeron el bug cuando se revirtió el fix.
- `docker compose up -d --wait` reusa la imagen cacheada; si sólo `COPY` cambia o si el código de runtime cambia, hay que `docker compose build --no-cache backend` explícitamente. La validación estática del Dockerfile no basta; la imagen anterior sigue existiendo y el healthcheck falla por algo que ya arreglaste.
- asyncpg devuelve `bytes` (no `str`) para las columnas `char`/`"char"` de `pg_catalog` (`pg_constraint.contype`, `pg_constraint.confdeltype`). Comparar `row["kind"] == "f"` siempre falla; usar `bytes(row["kind"]) == b"f"`. Misma trampa con `pg_index.indisunique` y similares. Si los tests offline pasan porque el assert compara contra `bytes` casualmente, el assert no testea nada cuando corre contra PG real.
- `StarletteDeprecationWarning` en Starlette 1.8 es subclase de `UserWarning`, no de `DeprecationWarning`. Un `filterwarnings = ["error", "ignore::DeprecationWarning:starlette.*"]` no la silencia y el collect de pytest revienta con `StarletteDeprecationWarning: Using httpx with starlette.testclient is deprecated; install httpx2 instead`. Hay que añadir `ignore::starlette.exceptions.StarletteDeprecationWarning` explícitamente.
- `docker run --no-deps <image>` no existe como flag de `docker run`; el flag vive en `docker compose run --no-deps <service>`. Usar `docker compose -f <file> run --rm --no-deps <service> sh -c "..."` para ejecutar comandos dentro de la imagen sin levantar sus dependencias.
- Aislamiento entre proyectos Compose: el `name:` top-level (`name: usher-library`) y los `name:` por red/volumen (`usher_net`, `usher_postgres_data`, etc.) hacen que un segundo proyecto `-p foo` colisione en esos recursos. Para aislar el recorrido de verificación: (1) construir una copia temporal del compose sin los `name:` para que Compose prefije con `<project>_<key>`; (2) sobrescribir las variables de host-port (`BACKEND_PORT=18000`, `FRONTEND_PORT=15173`); (3) reescribir bind-mounts relativos a rutas absolutas; (4) poner la copia temporal en una ruta del repo (no en `/tmp`) porque BuildKit sandbox no puede leer fuera de paths explícitos. La regex que elimina líneas `name:` debe tolerar la ausencia de `\n` final (la última línea del archivo a veces no lo trae y el `^name: usher_\S+\n` falla silenciosamente).
- Dos Keycloaks en la misma máquina con `--import-realm` forman un cluster JGroups/Infinispan a pesar de estar en redes Docker distintas: el Keycloak recién arrancado descubre el H2 embebido del Keycloak de desarrollo, intenta JDBC_PING y muere con `Sleep interrupted`. Aislamiento de redes no basta: hay que fijar `KC_CACHE=local` (devuelve la caché a local-only) en el proyecto de verificación para que JGroups no entre en juego.
