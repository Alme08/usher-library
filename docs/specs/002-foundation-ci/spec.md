# Spec 002 — Foundation: verificación automática y documentación
Estado: aprobada

## Contexto y objetivo
Esta spec resulta de dividir la fase Foundation original por exceder el límite de tareas del flujo SDD. **Depende de la spec 001** (`docs/specs/001-foundation/`), ya cerrada: deja el entorno de desarrollo ejecutable y fue verificada con runtime real (2026-10-14, commit `ee86a00`). La verificación estática de la 001 no detectó tres defectos reales que solo aparecieron al ejecutar: la imagen del backend no embarcaba la configuración de migraciones, el arranque resolvía mal la ruta de esa configuración, y la definición del realm usaba campos no soportados por la versión del proveedor de identidad, de modo que ese servicio moría en bucle y el stack nunca llegaba a healthy. Esos tres defectos son la justificación del alcance de esta spec: la verificación debe ejecutar el sistema, no solo inspeccionarlo.

El plan de la 001 (§6) delegó explícitamente en esta spec la automatización de: (a) el ciclo de migraciones `aplicar → revertir → aplicar` con comprobación del esquema resultante, y (b) el recorrido de arranque completo (comando único desde clon limpio, rearranque desde cero, conflicto de puerto). Esta spec cubre ambas deudas.

Sobre esa base, la spec añade dos cosas: (1) la **verificación automática** de todo cambio en la plataforma de integración continua fijada por la arquitectura (GitHub Actions, `docs/architecture/overview.md` §20), que ejecuta las suites de cada stack, los tests de integración de base de datos, el ciclo de migraciones con validación del esquema y el recorrido de arranque con el stack completo; (2) la **documentación pendiente** que Foundation hace necesaria: el documento de arquitectura de infraestructura (referenciado por la arquitectura y el README, inexistente hoy) y los ADRs iniciales, conforme al principio 1 de la constitución.

**Prerrequisito del usuario:** el repositorio hospedado en GitHub ya existe y está conectado como remote `origin` (la rama `main` sigue a `origin/main`, sin commits locales sin publicar); quedan por confirmar por el usuario la visibilidad del repositorio y que GitHub Actions esté habilitado, porque en el entorno de trabajo no hay herramienta para auditarlo. Esta spec entrega en el repositorio los flujos de trabajo y su documentación, y la verificación de la integración continua en verde se cierra cuando alguien publica esos flujos en el remote y se observa una ejecución real en verde (ver «Fuera de alcance»).

## Usuarios
- Desarrolladores del proyecto (no hay funcionalidad de producto para lectores).
- Mantenedores del repositorio y de la infraestructura.

## Historias de usuario
- HU-1. Como desarrollador, quiero que cada push y cada pull request se verifiquen automáticamente para detectar errores antes de integrar.
- HU-2. Como desarrollador, quiero que las migraciones se validen automáticamente, incluido el ciclo aplicar → revertir → aplicar y que el esquema final coincida con el modelo de datos documentado, para confiar en su reversibilidad antes de integrar.
- HU-3. Como desarrollador, quiero que el recorrido de arranque del stack completo se verifique automáticamente (servicios healthy, comprobación de vida, importación del realm, rearranque desde cero, conflicto de puerto) para detectar los fallos que la verificación estática no ve.
- HU-4. Como desarrollador, quiero ejecutar localmente las mismas verificaciones que la integración continua con un único comando documentado, sin destruir los datos de mi entorno.
- HU-5. Como mantenedor, quiero la infraestructura de contenedores, el despliegue y el flujo de verificación automática documentados para que las decisiones operativas sean reproducibles y revisables.
- HU-6. Como mantenedor, quiero que cada dependencia, servicio o herramienta mayor tenga su ADR y que los menores queden registrados de forma agregada, para que ninguna incorporación quede sin justificación aprobada.
- HU-7. Como mantenedor, quiero una única definición de la verificación del proyecto para que local, integración continua y AGENTS.md no diverjan.

## Definiciones
- **Verificación automática**: ejecución, en la plataforma de integración continua fijada por la arquitectura, de cuatro bloques: (1) suites de cada stack (lint, comprobación de tipos, tests y compilación en frontend; lint y tests en backend); (2) tests de integración de base de datos; (3) ciclo de migraciones con validación del esquema final; (4) recorrido de arranque con el stack completo. Sin publicación ni despliegue. Su contenido es el mismo que la sección «Verificación» de AGENTS.md define una vez actualizada por esta spec (RF-10): una sola definición.
- **Stack completo**: los cinco servicios del entorno definido en la spec 001: base de datos, almacén de estado temporal, proveedor de identidad, backend y frontend.
- **Tests de integración de base de datos**: tests automatizados de la suite del backend que se ejecutan contra una base de datos real levantada en el entorno (nada de dobles): comprueban el esquema inicial completo del modelo de datos (las 11 tablas del «Initial Schema» de `docs/architecture/database.md` §30, con sus restricciones e índices) y las sondas reales de conectividad a la base de datos y al almacén de estado temporal. Quedan en el repositorio y son reutilizables en local y en la integración continua.
- **Base de datos desechable**: base de datos vacía creada solo para la verificación y destruida al terminar; nunca es el volumen persistente de desarrollo del desarrollador.
- **Ciclo de migraciones**: secuencia aplicar → revertir hasta la base → aplicar sobre una base de datos desechable inicialmente vacía.
- **Recorrido de arranque**: comprobación de que, desde un estado limpio, el comando documentado de arranque deja el stack completo en estado healthy; la comprobación de vida del backend responde 200 con la base de datos y el almacén temporal accesibles; el proveedor de identidad importa su realm sin errores; un rearranque desde cero reproduce el entorno; y un conflicto de puerto provocado falla con un mensaje que identifica la causa.
- **Dependencia, servicio o herramienta mayor**: aquella que cumple al menos una de estas condiciones: (a) servicio de infraestructura que corre como proceso o contenedor propio en el entorno; (b) framework o runtime que estructura un stack completo de la arquitectura (figura en las «Confirmed technology choices» de `docs/architecture/overview.md` §20); (c) la plataforma de integración continua. Todo lo demás (linters, formateadores, runners de tests del toolchain estándar del stack, devDependencies y librerías de apoyo de un mayor) es **menor**.
- **ADR (registro de decisión arquitectónica)**: documento breve en `docs/decisions/` que registra una decisión, su contexto, las alternativas consideradas y sus consecuencias, siguiendo el principio 1 de la constitución.
- **Repositorio hospedado**: el remote de GitHub del proyecto (`origin`), ya creado y conectado por el usuario.

## Requisitos funcionales
- RF-1: CUANDO se realice un push o se abra o actualice una pull request en el repositorio hospedado, EL SISTEMA ejecutará automáticamente la verificación automática completa sobre el cambio.
- RF-2: MIENTRAS se ejecute la verificación automática, EL SISTEMA ejecutará las suites de cada stack con el runner propio de ese stack: lint, comprobación de tipos, tests y compilación en el frontend; lint y tests en el backend.
- RF-3: EL SISTEMA incluirá tests de integración de base de datos en el repositorio, ejecutables con el runner del stack backend tanto en local como en la verificación automática, que contra una base de datos real comprueben: (a) el esquema inicial completo del modelo de datos (11 tablas con sus restricciones e índices); y (b) las sondas reales de conectividad a la base de datos y al almacén de estado temporal.
- RF-4: MIENTRAS se ejecute la validación de migraciones en la verificación automática, EL SISTEMA ejecutará el ciclo de migraciones sobre una base de datos desechable inicialmente vacía.
- RF-5: CUANDO el ciclo de migraciones termine, EL SISTEMA comprobará que el esquema final coincide con el esquema inicial documentado del modelo de datos (tablas, restricciones e índices); SI la reversión omite algún elemento, ENTONCES la comprobación fallará aunque el ciclo haya terminado sin error.
- RF-6: CUANDO se ejecute la verificación automática, EL SISTEMA comprobará el recorrido de arranque completo: el comando documentado de arranque (`docker compose -f infra/docker-compose.yml up -d --wait`) deja el stack completo healthy; `GET /health` responde 200 con las sondas de base de datos y almacén temporal correctas; el proveedor de identidad importa su realm sin errores; tras detener el entorno y eliminar su estado, un rearranque desde cero lo reproduce; y un conflicto de puerto provocado falla con un mensaje que identifica la causa.
- RF-7: MIENTRAS se ejecute la verificación automática, EL SISTEMA aplicará timeouts explícitos y acotados a cada trabajo; SI un servicio del stack no llega al estado healthy dentro de su timeout, ENTONCES EL SISTEMA hará fallar la verificación identificando qué servicio no llegó y adjuntando sus logs.
- RF-8: SI cualquiera de las verificaciones automáticas falla, ENTONCES EL SISTEMA marcará la integración del cambio como fallida, con el resultado visible para su autor en el repositorio hospedado.
- RF-9: EL SISTEMA incluirá un comando único local, documentado en el README, que ejecuta las mismas verificaciones que la verificación automática (suites por stack, tests de integración de base de datos, ciclo de migraciones y recorrido de arranque con el stack completo) apoyándose únicamente en el runtime de contenedores y en un script de shell del repositorio; el ciclo de migraciones y los tests de integración se ejecutan sobre una base de datos desechable, sin destruir los datos del volumen de desarrollo del desarrollador.
- RF-10: EL SISTEMA mantendrá la sección «Verificación» de AGENTS.md como definición única de la verificación del proyecto, actualizada por esta spec para incluir la compilación del frontend y la verificación del stack completo con Compose.
- RF-11: EL SISTEMA incluirá el documento de arquitectura de infraestructura (`docs/architecture/infrastructure.md`, referenciado por la arquitectura y el README, inexistente hasta ahora) que describa contenedores, topología de desarrollo (puertos directos, sin proxy inverso), topología de producción (con proxy inverso), despliegue y el flujo de verificación automática.
- RF-12: EL SISTEMA incluirá en `docs/decisions/`: (a) un ADR individual por cada dependencia, servicio o herramienta mayor introducida en la fase Foundation —a fecha de esta spec: PostgreSQL, Redis, Keycloak, Docker/Docker Compose, FastAPI y React + TypeScript + Vite— y un ADR de la plataforma de integración continua (GitHub Actions), que es decisión de esta spec; y (b) un único ADR agregado que registre las decisiones menores (linters, devDependencies, runners de tests, librerías de apoyo), incluidas las decisiones registradas provisionalmente en el plan de la spec 001. La lista cerrada de elementos mayores se congela en el plan de esta spec.

## Requisitos no funcionales
- RNF-1: EL SISTEMA ejecutará los tests de cada stack con el runner propio de ese stack, conforme al principio 4 de la constitución.
- RNF-2: EL SISTEMA permitirá que un desarrollador ejecute localmente las mismas verificaciones que corre la integración continua (RF-9), sin configuración adicional más allá del entorno ya definido en la spec 001 y sin introducir runners nuevos: solo el runtime de contenedores y un script de shell del repositorio.
- RNF-3: EL SISTEMA mantendrá los timeouts de la verificación automática explícitos, acotados y registrados en la propia configuración de los flujos de trabajo.
- RNF-4: EL SISTEMA mantendrá los flujos de trabajo y los scripts de verificación libres de secretos y credenciales, conforme a la constitución.

## Casos límite
- Push que solo modifica documentación: la verificación automática sigue ejecutándose y pasando, sin comportamientos especiales.
- Verificación automática fallida en una rama: el fallo queda marcado y visible para el autor del cambio (RF-8); no bloquea su trabajo local. Bloquear la integración mediante reglas de protección de rama en la plataforma de hospedaje está fuera de alcance de esta spec.
- Servicio del entorno de integración continua que tarda en estar listo: el recorrido de arranque espera a su disponibilidad dentro del timeout explícito del trabajo, en lugar de fallar en falso.
- Servicio que muere en bucle y nunca llega a healthy (precedente real: el realm del proveedor de identidad con campos no soportados en la spec 001): la verificación falla dentro del timeout identificando el servicio que no llegó y adjuntando sus logs (RF-7).
- Migración cuya reversión está rota: la validación del ciclo (RF-4) falla identificando la migración afectada.
- Reversión que termina sin error pero omite una restricción o un índice: la comprobación del esquema final (RF-5) falla aunque el ciclo haya completado.
- Volumen de desarrollo local con datos existentes: el comando local (RF-9) ejecuta el ciclo de migraciones y los tests de integración sobre una base de datos desechable, sin destruir esos datos.
- Realm del proveedor de identidad con campos no soportados por su versión: la comprobación de importación del realm del recorrido de arranque (RF-6) falla.
- Repositorio hospedado con GitHub Actions sin habilitar o con la visibilidad pendiente de confirmar: los flujos de trabajo y el comando local funcionan en el repositorio local; la ejecución automática en push y pull request se activa cuando el usuario habilita Actions y publica los flujos en el remote (prerrequisito).
- Dependencia o herramienta introducida sin ADR: la fase no puede cerrarse hasta que el ADR correspondiente existe (RF-12, principio 1 de la constitución).

## Fuera de alcance
- Publicar los cambios en el repositorio hospedado (push) y habilitar o confirmar GitHub Actions y la visibilidad del repositorio: son acciones del usuario en la plataforma de hospedaje; el remote `origin` ya existe y está conectado. Esta spec entrega los flujos de trabajo y su documentación; la verificación de la integración continua en verde en la rama principal se cierra cuando el usuario publica los flujos y se observa una ejecución real en verde.
- Configuración de reglas de protección de ramas o de checks obligatorios en la plataforma de hospedaje del repositorio.
- Publicación de imágenes de contenedor, despliegue continuo (CD) y aprovisionamiento de un entorno de producción real. El documento de infraestructura describe el despliegue, pero no se ejecuta.
- Pruebas automatizadas de extremo a extremo con navegador.
- Umbrales de cobertura u otras puertas de calidad distintas de la verificación automática definida.
- ADRs de tecnologías aún no introducidas en el repositorio (por ejemplo, el proxy inverso de la topología de producción): su registro corresponde a la spec que las introduzca.
- Nuevos runners, herramientas de automatización locales o servicios de infraestructura más allá del runtime de contenedores y un script de shell del repositorio (RNF-2).
- Cualquier funcionalidad de producto.
- Modificar requisitos de la spec 001; cualquier cambio en el entorno de desarrollo se tramita como cambio sobre esa spec.

## Criterios de finalización
1. Con el repositorio hospedado conectado (prerrequisito del usuario), la verificación automática está configurada y en verde en la rama principal, se ejecuta en push y pull request, e incluye las suites de cada stack, los tests de integración de base de datos, el ciclo de migraciones y el recorrido de arranque (RF-1, RF-2). Un cambio que rompe lint, tipos, tests o compilación queda marcado como integración fallida y visible para su autor (RF-8).
2. Los tests de integración de base de datos existen en el repositorio, pasan en local y en la integración continua contra una base de datos real, y comprueban el esquema inicial completo (11 tablas con restricciones e índices) y las sondas de conectividad (RF-3).
3. La validación de migraciones ejecuta el ciclo aplicar → revertir → aplicar sobre una base de datos desechable vacía y comprueba que el esquema final coincide con el modelo documentado; un fallo u omisión de la reversión rompe la integración identificando la migración (RF-4, RF-5).
4. El recorrido de arranque se verifica en la integración continua: el comando documentado deja el stack completo healthy, `GET /health` responde 200 con las sondas correctas, el realm se importa sin errores, el rearranque desde cero reproduce el entorno y el conflicto de puerto provocado falla con mensaje que identifica la causa; si un servicio nunca llega a healthy, el trabajo falla dentro de su timeout nombrando el servicio y adjuntando sus logs (RF-6, RF-7).
5. El comando único local documentado en el README ejecuta las mismas verificaciones que la integración continua, incluidos el stack completo y el ciclo de migraciones sobre una base de datos desechable, sin destruir los datos del volumen de desarrollo (RF-9, RNF-2).
6. La sección «Verificación» de AGENTS.md incluye la compilación del frontend y la verificación del stack completo con Compose, y es la única definición de verificación del proyecto (RF-10).
7. El documento `docs/architecture/infrastructure.md` existe y cubre contenedores, topología de desarrollo y de producción, despliegue y el flujo de verificación automática (RF-11).
8. Existen ADRs en `docs/decisions/`: uno individual por cada dependencia, servicio o herramienta mayor (incluida la plataforma de integración continua) y el ADR agregado de decisiones menores; ninguna dependencia, servicio o herramienta introducida en Foundation queda sin cobertura de ADR (RF-12).

## Dudas abiertas
Resueltas en la ronda de clarificación (decisiones del usuario sobre la revisión de QA): alcance de la verificación con el stack completo; los tests de integración de base de datos los crea esta spec y validan el esquema documentado; el ciclo de migraciones valida el esquema final; ADRs individuales para mayores más uno agregado para menores con criterio de «mayor» definido; el repositorio hospedado es prerrequisito del usuario; la protección de rama queda fuera de alcance y el fallo se marca visible sin bloquear; esta spec actualiza la sección «Verificación» de AGENTS.md; timeouts explícitos con identificación del servicio y sus logs; comando local único sin runners nuevos.

Sin dudas abiertas que bloqueen la aprobación. Quedan diferidos al plan (no son dudas de requisitos): los valores concretos de timeout por trabajo y la lista cerrada de elementos mayores para los ADRs, que se congela en `plan.md` (RF-12).
